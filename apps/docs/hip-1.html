HIP-1: Agent Capability Cards.

An open convention for machine-readable agent identity on Base: a small set of text records on a .hawk name, and one verification algorithm any counterparty can run.

Abstract.

A capability card is the machine-readable profile of an on-chain agent, published as standard ENS text records on the agent’s .hawk name. Because the records live in ENS-standard infrastructure, every wallet, explorer, and library that speaks ENS can already read them — this document only fixes the vocabulary and the verification algorithm so that independent implementations agree on what “verified” means.

Motivation.

Agents transact with counterparties they have never met. Before trusting bot1.acme.hawk a counterparty needs three answers with cryptographic backing: is this name real, which account does it act from, and who does it answer to? Self-hosted allowlists don’t compose; bespoke registry contracts fragment tooling. Text records on a hierarchical name answer all three with infrastructure that already exists, at the cost of agreeing on a few keys — which is this spec.

Specification — the records.

A capability card is set on a registered .hawk name (a 2LD like acme.hawk or a subname like bot1.acme.hawk) through its resolver. Requirement language follows RFC 2119.

recordlevelvalue
address (coinType 60) MUST the account the agent acts from — setAddr(node, account). Without it the name cannot verify.
agent.capabilities MUST comma-separated lowercase verbs: swap,quote,settlement. Publishing a non-empty value is the opt-in that lists the agent in the directory; clearing it delists.
url SHOULD HTTPS endpoint where the agent (or its API / A2A interface) is reachable.
description SHOULD one or two plain-text sentences: what this agent does.
agent.model MAY model / runtime identifier, free text.
agent.operator MAY informative operator label. The cryptographic operator is always the parent name — this record never overrides it.
avatar MAY image URI, standard ENS avatar format.

Future keys in this convention MUST use the agent. namespace. Capability verbs are free-form; implementations MUST treat unknown verbs as opaque strings. A short common vocabulary (non-normative): swap, quote, lend, rebalance, settlement, payments, custody, data, oracle, compute, social.

Specification — verification.

Given a claimed name, a conforming verifier computes:

  1. Normalize the name per ENSIP-15; reject on failure. Compute node = namehash(name).
  2. registered — the node exists in the registry (a 2LD registration, or an issued subname).
  3. rootActive — the name’s 2LD ancestor (acme.hawk for bot1.acme.hawk) is unexpired: expiry > now. A name in its grace period is not active. Every agent inherits its root’s liveness — if the root lapses, the whole fleet fails verification.
  4. addressSet — addr(node, 60) is non-null.
  5. verified = registered ∧ rootActive ∧ addressSet.
  6. primaryMatch (optional, strongest signal) — the address’s reverse record resolves to exactly this name. Only the account holder can set it, so it binds name and account in both directions. Verifiers SHOULD report it; high-value counterparties SHOULD require it.
  7. Operator chain — walk successive parents up to the 2LD and report each ancestor’s name and owner. This is the delegation proof: an agent answers to its chain, or it doesn’t resolve under it.

Freshness. Verdicts are point-in-time reads of live chain state. Consumers MUST NOT cache a verdict beyond 60 seconds. Revocation needs no announcement: the operator clears the address record, deletes the subname, or lets the root expire — and the name stops verifying for everyone on the next read.

Reference implementation.

curl -s https://api.dothawk.xyz/verify/genesis.hawk

Open CORS, ~30 s cache. Returns the checks above plus the operator chain and the full capability card. The directory feed is GET api.dothawk.xyz/agents (?operator= filters a fleet). Both are convenience surfaces over public chain state — anyone can recompute every answer from Base directly, with no permission from hawk.

On-chain, without the API.

import { createPublicClient, http } from "viem";
import { base } from "hawk-names";

const client = createPublicClient({ chain: base, transport: http() });
const address = await client.getEnsAddress({ name: "bot1.acme.hawk" });   // addressSet
const primary = await client.getEnsName({ address });                     // primaryMatch
const caps    = await client.getEnsText({ name: "bot1.acme.hawk", key: "agent.capabilities" });

Security considerations.

  • Capability cards are self-attested. Verification proves identity and delegation — which account, answering to which operator — never competence, honesty, or safety. swap in a record means the operator says it swaps.
  • Trust the chain, not the label. agent.operator is informative; the operator that counts is the parent name in the namehash chain.
  • Require the round-trip for value. Anyone can point a name at any address, but only the address holder can point back. Before sending funds, demand primaryMatch.
  • Expiry is a feature. Roots lapse; verdicts go stale in seconds. Re-verify per session, not per relationship.

Versioning.

This document is v1 and covers everything the live verifier implements. Additive keys (new agent.* records) do not change the version. Any change to the verification algorithm is a new HIP.
